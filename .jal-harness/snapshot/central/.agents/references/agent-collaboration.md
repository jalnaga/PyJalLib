# 에이전트 협업과 인수 검증

## 실행 계층과 역할

- 사용자 지정 기준 checkout의 단일 코디네이터가 독립 작업별 전용 브랜치·worktree 하나를 준비한다. 워커는 테스터·구현자 등 배정된 역할 에이전트이며 중간 코디네이터나 재귀 워커를 만들지 않는다.
- 실행 전 작업별 모드·범위·의존 관계를 보여주고 승인받는다. 기본은 자율형이며 사용자가 직접 보면서 수행하겠다고 한 작업만 개입형으로 둔다. 개입형은 사용자 완료 판정까지 기다린다.
- 승인 → 워크스페이스 생성 → 환경 준비 성공 확인 → 지시서 exclude·작성·배정 일치 확인 → ACTIVE_WORK 등록 → 테스터 실행·테스트 커밋 → 테스터 종료 확인 → 인수 기준 확정·구현자 역할 갱신 → 별도 구현자 실행 → 코디네이터 테스트·최종 판정 순서다. 생성과 시작이 결합된 호스트는 지시서 준비 전 작업하지 않는 동등한 대기 방식을 실증해야 한다.
- 테스터와 구현자는 같은 작업 worktree를 순서대로 쓰는 서로 다른 에이전트다. 테스터는 인수·회귀 보호 테스트와 UAT 절차·증거 안내를 준비해 종료한다. 다음 독립 작업의 테스터는 앞 구현 완료를 기다릴 필요가 없다.
- 구현자는 배정된 제품 코드와 명시적으로 허용된 내부 단위 테스트만 편집한다. 보호 테스트 수정은 코디네이터가 별도 테스터를 실행해 처리한다. 코디네이터가 코드 버전·dirty 상태·환경·데이터·결과·증거·미검증 항목으로 최종 판정하고 통합 후에도 재검증한다.
- 호스트가 작업공간·에이전트 가시성과 사용자 개입을 지원하면 내장 서브 에이전트보다 우선한다. 필요한 기능이 없으면 대체 방식의 한계와 질문·결과 반환 경로를 밝힌다. 사용자 설정·승인 권한을 임의 확대하지 않는다.

코디네이터가 현재 호스트의 공식 도구·문서·설치 버전별 스킬로 생성, 별도 에이전트 실행, 사용자 개입, 질문·결과 전달, 완료 확인을 확인한다. 같은 환경에서 불필요하게 반복하지 않는다. 제품별 명령과 근거 수준은 `host-adapters/`의 해당 문서에 두고 공통 계약은 `worker-task-contract.md`를 따른다. 자원별 관리 주체는 하나이며 별도 실행 관리자·스케줄러·실행 상태 장부·훅을 추가하지 않는다.

| 역할 | 책임 |
|---|---|
| 코디네이터 | 기준 위치·분할·모드·의존성·배치·지침 선별·소유권·실행 추적, 테스트 실행·최종 판정·통합 후 재검증 |
| 테스터 | 인수 조건과 보호 테스트·fixture·기대 결과·실행 설정, UAT 절차와 증거 안내를 작성·커밋 후 종료 |
| 구현자 | 제품 코드와 허용된 내부 단위 테스트를 구현하고 코드 버전·변경·검증·근거·남은 문제 반환 |

별도 검증 테스터의 상시 실행을 요구하지 않는다. 조사·검토·지식 정리는 필요할 때 코디네이터가 직접 배정하고 작업별 중간 코디네이터를 추가하지 않는다. 독립 에이전트를 실행할 기능이 없으면 사용자에게 별도 세션 실행을 요청하고 제한을 보고한다. 제품 코드·테스트·실행 도구 개발에서는 한 에이전트의 역할 전환으로 작성자·구현자 분리를 대체하지 않는다.

중앙 지식 검토·정제·통합(OKF concept·`log.md`·생성 색인·inbox 검토 이력·후보 PR 접수 편집)은 이 테스터→구현자 분리와 보호 테스트 감사의 대상이 아니다. 중앙 담당자 한 명(코디네이터 자신 또는 배정된 한 에이전트)이 검토와 문서 편집을 함께 수행하고, 자료·문서 무결성은 `knowledge-system.md`의 `knowledge-check`로 확인한다. 승격 PR용 전용 브랜치(필요 시 worktree)는 유지한다. 지식 편집과 도구 개발이 함께 요청되면 범위를 나눠 도구 변경만 위 개발 절차를 따른다. 문구·출처 메타데이터 보완 때문에 테스터·구현자를 실행하지 않는다.

## ATDD·TDD와 판정

테스터는 공개 동작과 사용자 결과를 기준으로 정상·경계·실패 사례를 작성한다. 자동화가 적합하면 기대 동작 또는 기존 버그 때문에 실패하는지 확인하고 준비·권한·의존성 같은 환경 오류와 구분한다. 자동화할 수 없는 항목에는 억지로 실패 테스트를 만들지 않고 UAT 절차를 준비한다. 구현자는 명시적으로 허용된 내부 단위 테스트에 실패→구현→통과→리팩터링의 TDD를 적용할 수 있다.

코디네이터는 테스트 기준 커밋 이후 커밋·미커밋·미추적 변경, 삭제·이름 변경 및 실행 제외·우회를 `worker-task-contract.md` 절차로 확인한다. 구현자는 보호 테스트·fixture·기대 결과·실행 설정을 삭제·완화·우회하지 않는다. 기준 변경이 필요하면 요구사항·근거를 확인해 별도 테스터를 실행하고 기준 커밋·지시서 인수 섹션을 다시 확정한다. 개입형 대화 중 사용자가 요청한 기준 변경도 같다.

| 인수 상태 | 의미 |
|---|---|
| `pass` | 해당 조건을 검사한 근거 충분 |
| `fail` | 기대와 다른 동작 확인 |
| `user_pending` | 사용자 실행·결과 또는 개입형 완료 판정 대기 |
| `insufficient_evidence` | 코드·환경·데이터·증거가 부족하여 판정 불가 |

테스터는 앱/엔진·코드/빌드 버전, 실제 데이터 조건과 안전한 사본, 준비·실행 순서, 기대 결과, 수집할 로그·화면·생성 데이터를 안내한다. 코디네이터가 도착한 증거의 코드 버전·dirty 상태·환경·데이터 일치와 충분성을 확인해 판정한다. 로그 무오류만으로 UI·기능·데이터 보존을 성공으로 판정하지 않는다. 민감한 데이터를 중앙으로 요구하지 않고 공유 로그에서 비밀·개인정보를 제거한다. 필수 `user_pending` 또는 `insufficient_evidence`가 남으면 완료 처리하지 않는다. 실패의 재현 조건을 구현자에게 전달하고 수정된 버전에서 필요한 항목을 재검사한다.

## 환경·의존성·결과

호스트의 저장소 setup 정책을 존중하고 코디네이터가 성공을 확인한 뒤 워커를 실행한다. 실패는 준비 오류이며 이미 성공한 준비를 불필요하게 반복하지 않는다. 실제 사용하는 포트·DB·컨테이너·브라우저 저장 데이터·외부 서비스는 격리하거나 순차 배정한다. 사용하지 않는 자원의 점검은 일률적으로 요구하지 않는다. 구체적인 설치·포트·분리 절차는 프로젝트 설정과 지시서에 둔다. 자율형과 개입형 모두 검증 코드·환경 일치를 확인한다.

강한 의존·겹치는 편집 범위는 순차 실행하거나 묶는다. 코디네이터가 다음 지시서에 선행 커밋·계약 변경·검증 결과·주의 사항과 base ref·반영 시점을 전달한다. 별도 영구 인계 채널은 추가하지 않는다. 질문·완료·실패·중단 결과와 직접 채널이 없을 때 반환·종료·재실행은 `worker-task-contract.md`를 따른다. native 완료 신호와 세션 식별자를 확인하고 상태가 불명확한 워커를 중복 실행하지 않는다.

## 독립 세션의 작업 발견과 공용 안내

사용자가 선택한 Git 저장소별 기준 checkout 루트에 `ACTIVE_WORK.md` 정본을 한 개 둔다. 기준 위치는 현재 환경의 작업 정보와 `git worktree list` 등 Git worktree 정보로 확인하며 현재 디렉터리·특정 브랜치 이름만으로 추정하지 않는다. 위치가 불명확하면 확인 전 새 안내를 만들지 않는다. 중앙과 독립 프로젝트는 각 Git 저장소의 기준 위치를 사용한다.

1. 첫 편집 전에 native 작업·터미널·worktree 정보와 정본을 읽어 기존 작업과 조정 담당을 발견한다. 다른 터미널·대화라는 이유로 기존 작업을 무시하지 않는다. 실제 실행 상태는 native 도구나 담당자에게 확인한다.
2. 조정자가 없거나 둘 이상 주장하면 먼저 지정·조율한다. 안내와 실제 상태가 충돌하거나 확인할 수 없으면 편집을 보류한다. 정본이 없으면 기존 작업 확인 후 지정 조정자가 최초 생성한다. 파일 부재는 다른 작업 없음의 증거가 아니다.
3. 조정자만 배치와 안내를 갱신한다. 안내는 로컬 운영 자료이며 기존 `.git/info/exclude`의 내용을 보존하면서 `/ACTIVE_WORK.md`를 추가해 Git 이력에서 제외한다. linked worktree에서는 Git 공통 디렉터리의 `info/exclude`를 확인한다. 이미 추적된 파일은 제외 규칙으로 해결되지 않으므로 편집 전에 조율한다. 관리 자산·resolver 반환 자료·snapshot에 안내를 추가하지 않는다.
4. 코디네이터는 기준 정본의 절대 경로를 전달하며 워커는 필요할 때 확인하고 자체 사본을 만들지 않는다. 안내는 최소 배치·소유권·검증 및 승인 근거만 담고 진행률·에이전트 실행 상태를 복제하지 않는다. 잠금이나 전역 동기화 기능을 제공하지 않으므로 실제 상태 확인을 대신할 수 없다.

공용 안내의 최소 형식:

```markdown
# 활성 작업 안내 (로컬 정본)
- 기준 checkout: <절대 경로와 확인 근거>
- 지정 조정자: <담당 식별자>
- 연락·도구 경로: <native 메시지/터미널/작업 확인 경로>

## <작업 식별자>
- 목적·관계: <보완·재개 / 독립 기능 / 선행 의존, 관련 작업>
- 모드: <자율형 / 개입형>
- worktree: <절대 경로>
- 브랜치: <실제 브랜치>
- 편집 소유권: <담당자별 파일·범위>
- native 작업 링크: <호스트 워크스페이스·작업·세션 식별자 또는 접근 경로>
- 선행 결과·버전·순서: <의존성이 있는 경우>
- 검증 근거: <정확한 diff·커밋, 결과·미검증 항목의 위치>
- 승인 근거: <승인 대상·범위·대화 근거 또는 통합 승인 대기>
- 보존·재개 책임: <정리 불가 또는 중단·취소 시 남은 자원과 담당>
```

## 추가 요청과 작업 배치

추가 요청마다 기존 작업의 보완·재개, 독립 기능, 선행 작업 의존을 판단하고 배치를 짧게 알린다. 같은 대화나 터미널이라는 이유로 한 위치에 누적하지 않는다. 보완·재개는 적절한 기존 위치를 재사용한다. 독립 기능은 첫 코드·테스트·기능 문서·설정 편집 전에 전용 브랜치와 worktree를 확보한다. 기본 checkout에서는 조사·계획, 조정자의 최소 안내 유지와 승인된 통합만 수행한다. 확보 실패를 기본 checkout 개발로 대체하지 않는다.

강한 의존성은 순차 실행하거나 한 작업으로 묶고 사용할 선행 결과·버전과 실행 순서를 명시한다. 기존 dirty 변경·다른 작업·사용자 프로세스를 보존한다. 이미 섞인 변경의 분리는 별도 작업으로 다룬다. 담당자 교체는 기존 소유자의 편집 중단을 확인한 뒤 변경·결정·검증·미완료 사항을 인계한다.

## 통합과 종료의 소유권

개발·검증 완료와 통합 승인은 구분한다. 일반 완료·아카이빙 요청, 테스트 통과나 개발 승인만으로 merge·삭제를 수행하지 않는다. 지정 조정자가 정확한 변경과 통합 대상 브랜치, 후속 재검증·보조 자원 정리·지식 후보 수집 범위를 제시해 명시적 승인을 받는다. native PR·merge 기능이 제공되면 우선 사용하되 승인 없는 원격 push·PR 게시를 하지 않는다. 변경 내용이나 대상이 바뀌면 다시 승인받는다.

통합 후 코디네이터가 실제 통합 커밋과 dirty 상태를 검사한다. 실패하면 완료 처리·자원 삭제 없이 보존한다. 정리·지식 검토·활성 항목 제거·중단과 취소의 상세 순서는 `workflow.md`를 따른다. 모든 환경의 파일 쓰기를 지침만으로 기계적으로 차단할 수 없다. 문서·설치 테스트 통과와 실제 에이전트 준수를 별도로 보고하고 한 환경의 결과를 다른 환경에 일반화하지 않는다.
