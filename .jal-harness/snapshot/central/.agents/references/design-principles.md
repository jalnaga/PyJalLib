# 설계 원칙

기존 코드와 현재 요구에 필요한 가장 단순한 설계를 선택한다. 아래 원칙은 패턴의 개수를 늘리는 규칙이 아니라 불필요한 복잡성을 막는 판단 기준이다.

## 기본 원칙

- **YAGNI:** 승인된 성공 기준에 필요하지 않은 기능·확장점·설정을 미리 만들지 않는다.
- **KISS:** 같은 요구를 충족한다면 개념·계층·상태 전이가 적은 설계를 택한다.
- **DRY:** 같은 지식이 여러 곳에서 독립적으로 변경되어 불일치할 때 통합한다. 우연히 비슷한 코드만 보고 성급하게 추상화하지 않는다.
- **SRP:** 변경 이유와 책임 경계를 기준으로 모듈을 나눈다. 파일·클래스 수 자체를 목표로 삼지 않는다.
- **기존 구조 우선:** 안전·호환성 문제를 만들지 않는 한 저장소의 관례와 이미 존재하는 추상화를 따른다.

## 의존성 선택 순서

새 의존성이나 구현을 추가하기 전에 다음 순서로 확인한다.

1. 언어 표준 라이브러리와 플랫폼 기본 기능
2. 저장소에 이미 설치된 의존성
3. 저장소의 기존 구현이나 공용 모듈
4. 요구를 충족하는 최소한의 새 구현 또는 의존성

새 의존성은 유지보수·보안·배포 비용을 정당화할 때만 추가한다. 사용자 승인이나 저장소 정책이 요구되면 먼저 확인한다.

## 조건부 패턴

- **Dependency Injection:** 외부 효과를 격리하거나 구현 교체·테스트 경계·수명 관리가 실제로 필요할 때 사용한다. 단순 값 전달을 위해 컨테이너나 계층을 추가하지 않는다.
- **Facade:** 복잡한 서브시스템에 안정적인 단일 진입점이 필요할 때 사용한다. 이미 단순한 API를 다시 감싸지 않는다.
- **Service:** 상태와 규칙이 결합된 명확한 도메인 책임이 있을 때 사용한다. 함수 몇 개를 묶기 위한 이름표로 만들지 않는다.
- **Utility:** 상태가 없고 여러 사용처에서 같은 의미로 재사용되는 연산에 사용한다. 도메인 규칙을 잡다한 유틸리티에 숨기지 않는다.
- **Data Class:** 데이터 계약, 검증, 직렬화 또는 값 의미가 필요할 때 사용한다. 단순 전달에 불필요한 래퍼를 만들지 않는다.

## 구현 품질

- 공개 동작과 호환 계약을 먼저 확인하고 내부 구현은 그 경계 안에서 바꾼다.
- 언어가 지원하면 타입을 명시하되 기존 프로젝트의 타입 체계와 도구를 따른다.
- 입력 검증, 오류 처리, 보안, 접근성, 리소스 정리는 최소 구현을 이유로 생략하지 않는다.
- 주석은 코드가 그대로 말하지 못하는 의도·제약·이유를 설명한다. 동작을 한 줄씩 번역하는 주석은 추가하지 않는다.
- 구조화된 프로젝트 로거가 있으면 사용하고 임시 출력은 완료 전에 제거한다.
