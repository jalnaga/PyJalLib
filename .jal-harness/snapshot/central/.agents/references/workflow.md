# 중앙·프로젝트 작업 흐름

## 코디네이터 시작과 계획

워커의 시작·재개는 프로젝트 AGENTS.md의 네 가지 분기와 `worker-task-contract.md`를 따른다. 아래 탐색·배치 절차를 워커에게 반복시키지 않는다.

1. 대상 Git 상태와 가까운 지침, native 작업·터미널·worktree 정보를 확인한다. 사용자 지정 기준 checkout을 환경 정보와 Git worktree 정보로 확인하고 그 루트의 `ACTIVE_WORK.md` 정본을 읽는다. 현재 디렉터리·브랜치 이름만으로 기준 위치를 추정하지 않는다.
2. 조정자가 없거나 복수인 경우 먼저 지정·조율한다. 정본이 없으면 기존 작업 확인 후 조정자가 최초 생성한다. 부재는 다른 작업 없음의 증거가 아니다. 기준 위치가 불명확하거나 안내와 실제 상태가 충돌·확인 불가이면 편집을 보류한다. 형식과 exclude 절차는 `agent-collaboration.md`를 따른다.
3. 원격 중앙 연결 프로젝트의 기준 checkout 코디네이터는 미완료 제출 기록을 설치된 플러그인의 `project-workflow.py submission-status <project> --refresh --startup --role coordinator`로 확인한다. 마지막 확인 시각·실패 이유를 유지하며 조회 실패·중앙 검토 대기는 개발 비차단이다. 워커·매 작업 worktree는 반복 조회하지 않는다. 상태 조회는 중앙 sync나 snapshot refresh를 하지 않으며 각각 별도 명시 승인과 미리보기를 유지한다. 이어서 프로젝트에서는 resolver의 `startup_files`와 `documents` 색인, `domain_indexes`의 도메인 index를 시작 시 읽고 현재 계획·결정에 필요한 중앙 공통·도메인 본문만 읽는다. `files`와 `verified_files`는 파일 검증 목록이며 전체 읽기 지시가 아니다. 요약으로 본문 규칙을 추정하지 않고 범위 변경·새 문제 발생 시 색인을 다시 참고한다. 이미 읽은 동일 버전 본문은 불필요하게 반복해서 읽지 않는다. 중앙 없이 사용하는 snapshot은 중앙 커밋과 오래된 상태를 알린다.
4. 기본 Plan 기능으로 목표·성공 기준·범위·제약을 조율한다. PRD·Tasklist는 선택이며 기존 기록·템플릿은 보존한다. 추가 요청은 보완·재개, 독립 기능, 선행 의존으로 판단해 배치를 알린다.
5. 사용자 지정 기준 checkout의 단일 코디네이터가 독립 작업별 전용 브랜치·worktree 하나를 준비한다. 워커는 테스터·구현자 등 배정된 역할 에이전트이며 중간 코디네이터나 재귀 워커를 만들지 않는다.

실행 전 작업별 모드·범위·의존 관계를 보여주고 승인받는다. 기본은 자율형이며 사용자가 직접 보면서 수행하겠다고 한 작업만 개입형으로 둔다. 개입형은 사용자 완료 판정까지 기다린다.

승인 → 워크스페이스 생성 → 환경 준비 성공 확인 → 지시서 exclude·작성·배정 일치 확인 → ACTIVE_WORK 등록 → 테스터 실행·테스트 커밋 → 테스터 종료 확인 → 인수 기준 확정·구현자 역할 갱신 → 별도 구현자 실행 → 코디네이터 테스트·최종 판정 순서다. 생성과 시작이 결합된 호스트는 지시서 준비 전 작업하지 않는 동등한 대기 방식을 실증해야 한다.

테스터와 구현자는 같은 작업 worktree를 순서대로 쓰는 서로 다른 에이전트다. 테스터는 인수·회귀 보호 테스트와 UAT 절차·증거 안내를 준비해 종료한다. 다음 독립 작업의 테스터는 앞 구현 완료를 기다릴 필요가 없다.

구현자는 배정된 제품 코드와 명시적으로 허용된 내부 단위 테스트만 편집한다. 보호 테스트 수정은 코디네이터가 별도 테스터를 실행해 처리한다. 코디네이터가 코드 버전·dirty 상태·환경·데이터·결과·증거·미검증 항목으로 최종 판정하고 통합 후에도 재검증한다.

호스트가 작업공간·에이전트 가시성과 사용자 개입을 지원하면 내장 서브 에이전트보다 우선한다. 필요한 기능이 없으면 대체 방식의 한계와 질문·결과 반환 경로를 밝힌다. 사용자 설정·승인 권한을 임의 확대하지 않는다.

## 실행과 재개

- 중앙은 공통 지침·OKF 지식 번들·등록부·중앙 후보를, 프로젝트는 코드·고유 지침·프로젝트 후보를 소유한다. 같은 작업에서 둘을 바꾸면 범위와 근거를 연결한다.
- 위 테스터→구현자 순서는 제품 코드·테스트·실행 도구 변경에 적용한다. 중앙 지식 검토·정제·통합은 중앙 담당자 한 명이 전용 브랜치에서 검토와 문서 편집을 함께 수행하고 `knowledge-check <central> --base <기본 브랜치>` 통과와 `CHECK_SHA256`을 검증 근거로 남긴다. 지식 편집과 도구 개발이 함께 요청되면 범위를 나눠 도구 변경만 개발 절차로 진행한다. 이 검사는 자료·문서 무결성 검사이며 지식 주장의 사실 검증이나 제품 테스트 통과로 보고하지 않는다.
- 보완·재개는 적절한 기존 작업 위치를 재사용한다. 독립 기능은 병렬 여부와 관계없이 분리하고 강한 의존은 순차 실행하거나 한 작업으로 묶어 선행 결과·버전·순서를 명시한다.
- 조정자는 최소 배치·소유권 안내를 유지하며 실행 상태는 native 도구나 담당자에게 확인한다. 진행률이나 에이전트 실행 상태를 별도 장부로 복제하지 않는다. 각 worktree는 정본을 읽고 자체 사본을 만들지 않는다.
- 에이전트 수와 worktree 수는 별개다. 편집 범위별 소유자는 한 명이다. 위임에 절대 경로·브랜치·범위·소유권·관련 작업·완료 기준을 포함하고 담당자는 실제 위치·브랜치를 확인한 뒤 편집한다. 잘못된 위치는 먼저 수정한다.
- 담당자 교체는 기존 소유자의 편집 중단 확인 후 변경·결정·검증·미완료 사항을 인계한다. 기존 dirty 변경·다른 작업·사용자 프로세스를 보존하고 이미 섞인 변경 분리는 별도 작업으로 다룬다.
- 재개·인계가 필요할 때만 목표·결정·소유권·버전·미완료 작업·근거를 짧게 남긴다. 전체 대화 복제나 새 PRD·Tasklist 작성을 강제하지 않는다.

## 개발·검증 완료와 통합 승인

1. 코디네이터가 정확한 코드 버전·dirty 상태·환경·데이터 조건·결과·미검증 항목을 최종 판정한다. 필수 항목이 `user_pending` 또는 `insufficient_evidence`이면 전체 작업을 완료 처리하지 않는다. 같은 코드 상태에서 통과한 검증은 새 변경이나 남은 문제가 있을 때만 반복한다. 중앙 지식 정리도 같은 `CHECK_SHA256`에서 통과한 `knowledge-check`를 반복하지 않으며 문구·출처 메타데이터 보완 때문에 테스터·구현자를 실행하지 않는다.
2. 조정자가 변경 요약, 정확한 diff·커밋, 검증 결과와 미검증 항목을 제시한다. 개발·검증 완료 시에도 활성 안내는 유지하고 통합 승인 대기를 기록한다.
3. 통합 대상 브랜치와 후속 재검증·보조 worktree/브랜치 정리·지식 후보 수집 범위를 함께 제시하고 명시적 승인을 받는다. 일반 완료·아카이빙 요청, 테스트 통과나 개발 승인을 merge 승인으로 해석하지 않는다.
4. 지정 조정자가 승인된 변경과 대상만 통합한다. native PR·merge 기능이 제공되면 우선 사용한다. 원격 push·PR 게시·배포는 별도 승인 범위에서 수행한다. 변경 내용이나 대상이 바뀌면 다시 승인받는다. 중앙 지식의 접수·승격 PR 게시·병합·검토 이력 연결 push는 `knowledge-system.md`의 "승인 단위와 묶음 승인"에 따라 결정·diff·head·`knowledge-check` 결과를 묶어 필요한 시점에 승인받고, 승인 뒤 의미 불변 무결성 보완은 새 head와 함께 보고한다.
5. 코디네이터가 실제 통합 커밋과 dirty 상태를 기준으로 재검증한다. 통합 또는 검증 실패 시 완료 처리하거나 자원을 삭제하지 않고 변경·자원·실패 근거를 보존한다.

## 안전한 정리와 정상 종료

1. 통합·재검증 성공과 미커밋·미통합 변경 부재를 확인한 뒤 해당 작업의 보조 worktree·브랜치를 자원 관리 도구로 정리한다. 기준 checkout, 현재 사용 중인 위치, 다른 작업과 사용자 프로세스는 보존한다. 현재 위치의 정리는 지원되는 방식으로 세션을 옮기고 사용 중이 아님을 확인한 뒤 수행한다.
2. 정리할 수 없으면 이유·남은 자원·책임을 활성 안내에 유지한다. 청결이나 통합이 확인되지 않은 자원을 강제 삭제하지 않는다.
3. 재사용할 후보가 없으면 검토 결과만 기록한다. 있으면 근거·적용 조건·민감 정보 검토를 갖춰 등록 checkout의 outbox에 보존한다. 원격 중앙의 기본 방식은 `knowledge-system.md`의 후보 PR 제출이다. 최초 `submission-policy`에서 대상·후보·근거 공유 범위를 승인받은 뒤 같은 범위 아카이빙은 에이전트가 실제 내용과 새 미리보기를 검사하고 새 `PLAN_SHA256`으로 `submit --apply --expect-plan`을 실행한다. 같은 범위에 매번 사용자 승인을 요구하지 않는다. 실제 내용 변화는 재검토·새 미리보기를, 대상·공유 범위 변화는 정책 재승인도 요구한다. 로컬 등록 중앙의 `collect`도 유지한다.
   제출 실패는 원본 후보·근거·실패 사유·재시도 정보를 보존한 `pending`(제출 대기)이다. 정확한 원격 head·diff·manifest·프로젝트 출처 검증 뒤 저장한 성공 기록의 PR URL은 프로젝트 제출 책임 완료이며 중앙 접수·정식 승격·병합 승인은 별개다. 후보 없음은 `review.json`의 `no_candidates`, 병합 없는 기존 CLOSED는 자동 재게시 없이 `closed`로 남겨 판단을 요청한다. 제출 대기·종료 후보가 있으면 활성 안내에 담당과 재개 위치를 유지하거나 명시적으로 인계한 뒤 종료한다. 성공 기록 저장 뒤 후보만 탐색 밖 archive로 옮기고 공유 근거는 제자리에 보존한다. 이동 중단은 원격 ID·기록·archive로 복구한다. 구기록/혼재 근거는 `submission-migrate` 미리보기·적용으로 탐색 메타데이터만 이관하며 후보 참조와 공유 경로를 바꾸지 않는다. `submission-status`는 접수·승격 PR·정식 반영·프로젝트 적용 버전을 분리하며 unknown을 성공으로 보고하지 않는다. 원격 제출 전용 브랜치는 검토 근거이므로 작업 보조 worktree 정리와 함께 삭제하지 않는다. 정식 공용 지침 승격은 별도 검토·묶음 승인이다.
4. 정상 종료 조건 충족 후 활성 항목을 제거한다. 도구의 worktree 등록, 실제 경로, 브랜치와 안내 항목 제거를 확인하고 다른 작업의 보존을 보고한다. 완료 근거는 필요한 경우 선택 기록으로 보존하며 활성 목록에 누적하지 않는다.

## 중단·취소와 지식 환류

- 중단·취소는 정상 완료와 구분한다. 자동 merge·삭제를 하지 않고 변경·자원·재개 정보를 보존한다. 활성 항목을 제거하려면 별도 인계·보존 기록과 남은 자원의 책임을 먼저 확인한다. 재개 시 실제 자원·소유권·버전을 다시 확인한다.
- 워커 지식 후보는 코디네이터가 근거를 확인해 등록 checkout의 outbox에 통합한다. 중앙 수집은 후보 원본을 보존하고 정식 승격은 검토·승인 후 수행한다. 코디네이터의 다음 계획은 최신 색인을 확인하고 해당 계획에 필요한 정식 지식 본문만 읽는다.
- 실제 사용자 작업공간 갱신은 소스 개발과 별개다. 승인된 대상·파일 목록·diff·preview hash 범위만 적용하고 snapshot refresh는 별도 승인한다.
