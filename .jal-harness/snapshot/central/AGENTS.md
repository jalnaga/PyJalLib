# JalHarness Central Instructions

## 역할별 시작과 재개

다른 시작 절차보다 먼저 사용자·코디네이터의 배정과 작업 루트 `.jal-harness-task.md`를 확인한다.

- 배정 있음 + 지시서 일치: 배정된 워커로 시작한다.
- 배정 있음 + 지시서 누락·불일치: 편집을 보류하고 배정자에게 확인한다. 새 코디네이터로 전환하거나 추가 worktree를 만들지 않는다.
- 배정 없음 + 지시서 있음: 지시서의 역할·모드를 따르는 워커로 시작한다. 개입형 공간에 사용자가 직접 들어온 경우도 같다.
- 배정 없음 + 지시서 없음: 기준 checkout과 `ACTIVE_WORK.md`·native 작업을 확인하고 코디네이터 시작 절차를 따른다.

워커는 형식 버전·작업 ID·역할·워크트리 절대 경로·실제 브랜치·질문 경로를 배정과 대조한다. 지시서와 거기에 열거된 본문을 전부 읽는다. 이 본문 읽기는 탐색이 아니다. 워커는 resolver 실행, 중앙 색인 탐색, 목록 밖 중앙 본문 탐색, 중앙 해시 재검증이나 별도 고정 사본 생성을 하지 않는다. 부족한 지침은 자율형에서는 코디네이터, 개입형에서는 사용자에게 요청하고 해당 판단을 보류한다. 이후의 중앙 선택·배치·안내 갱신 절차는 코디네이터의 책임이며 워커의 반복 시작 절차가 아니다.

## 역할과 경계

- 이 저장소는 공통 지침과 도메인 지식을 관리한다. 사용자 요청과 더 가까운 프로젝트 `AGENTS.md`가 우선한다.
- 소속 프로젝트는 `.jal-harness/projects.json`에 등록한다. 프로젝트 코드와 Git 이력은 독립 저장소에 둔다. `repos/`는 기본 배치이며 외부 checkout도 허용한다.
- 중앙 정식 지식은 `.agents/references/` OKF 번들이다. 코디네이터 시작 시 AGENTS.md와 번들 루트 `index.md` 색인만 읽는다. 공통 concept의 frontmatter `description`·`applies_when`·`read_before`는 주제 요약·적용 조건·읽어야 할 시점을 제공하며 본문 규칙을 대신하지 않는다. 사용자 요청과 작업 범위에 필요한 공통 본문만 관련 계획·구현·검증이나 결정 전에 읽는다.
- 도메인 지식은 `.agents/references/domains/<도메인>/`에 있다. 해당 프로젝트 도메인의 `index.md`에서 필요한 문서만 점진적으로 찾아 읽고 다른 도메인은 읽지 않는다.
- 본문을 읽기 전에는 색인의 짧은 설명만으로 세부 규칙을 추정하거나 적용하지 않는다. 작업 범위 변경이나 새로운 문제 발생 시 색인을 다시 참고하고 필요한 본문을 추가로 읽는다. 이미 읽은 동일 버전 본문을 이유 없이 반복해서 읽지 않는다.
- 코디네이터는 필요한 지침 본문의 절대 경로와 출처(중앙 커밋·버전·source·stale)를 지시서로 전달한다. 중앙 요약본을 복제하지 않고 작업 고유 제약만 직접 적는다. 워커는 열거된 본문을 전부 읽되 출처를 재검증하지 않는다.

## 제출 상태 확인 경계

- 원격 중앙 연결 프로젝트의 기준 checkout 코디네이터만 시작 시 설치된 플러그인의 `project-workflow.py submission-status <project> --refresh --startup --role coordinator`로 미완료 기록을 확인한다. 마지막 성공 시각·실패 이유를 보존하며 네트워크 실패와 중앙 검토 대기는 개발을 막지 않는다.
- 이 조회는 중앙 sync·snapshot refresh와 별개다. 최신화는 각각 별도 명시 승인과 미리보기를 유지한다. 이어 resolver의 색인을 읽고 필요한 본문을 선택한 뒤 작업 worktree를 준비한다. 워커·매 작업 worktree에 원격 상태 조회를 반복시키지 않는다. worker의 상태 조회는 로컬 읽기 전용이다.
- 최초 정책과 submit의 `--candidate`는 같은 일회 선택이며 지속 승인 디렉터리를 바꾸지 않는다. 모든 승인 candidate_paths를 탐색하고 evidence/ 및 명시 분류한 정확한 경로/해시 근거만 제외한다. 구기록·혼재 자료는 `submission-migrate` 계획을 검토한 뒤 적용하며 공유 근거·후보 참조는 그대로 둔다.
- exact head·manifest·프로젝트 출처 blob·예상 inbox 밖 diff 부재를 검증한 성공 기록 저장 후 후보만 탐색 밖 archive로 옮긴다. `submission-status`의 제출·검토·승격·정식 반영·프로젝트 적용은 별개이며 unknown을 완료로 해석하지 않는다. 이 구분은 기록 구분이며 단계마다 별도 에이전트 실행이나 사용자 승인을 뜻하지 않는다. 제출 승인·접수 승인·승격 PR 게시/병합 승인도 별개이며 사용자가 명시적으로 함께 승인한 묶음만 한 번에 처리한다. 상세 계약은 중앙 `.agents/references/knowledge-system.md`를 따른다.

## 계획과 협업

- 사용하는 에이전트의 기본 Plan 기능으로 요구사항·성공 기준·실행 범위를 조율한다. PRD·Tasklist 생성이나 파일 저장은 필수가 아니다. 기존 기록과 선택 템플릿은 보존한다.
- 사용자 지정 기준 checkout의 단일 코디네이터가 독립 작업별 전용 브랜치·worktree 하나를 준비한다. 워커는 테스터·구현자 등 배정된 역할 에이전트이며 중간 코디네이터나 재귀 워커를 만들지 않는다.
- 실행 전 작업별 모드·범위·의존 관계를 보여주고 승인받는다. 기본은 자율형이며 사용자가 직접 보면서 수행하겠다고 한 작업만 개입형으로 둔다. 개입형은 사용자 완료 판정까지 기다린다.
- 승인 → 워크스페이스 생성 → 환경 준비 성공 확인 → 지시서 exclude·작성·배정 일치 확인 → ACTIVE_WORK 등록 → 테스터 실행·테스트 커밋 → 테스터 종료 확인 → 인수 기준 확정·구현자 역할 갱신 → 별도 구현자 실행 → 코디네이터 테스트·최종 판정 순서다. 생성과 시작이 결합된 호스트는 지시서 준비 전 작업하지 않는 동등한 대기 방식을 실증해야 한다.
- 테스터와 구현자는 같은 작업 worktree를 순서대로 쓰는 서로 다른 에이전트다. 테스터는 인수·회귀 보호 테스트와 UAT 절차·증거 안내를 준비해 종료한다. 다음 독립 작업의 테스터는 앞 구현 완료를 기다릴 필요가 없다.
- 구현자는 배정된 제품 코드와 명시적으로 허용된 내부 단위 테스트만 편집한다. 보호 테스트 수정은 코디네이터가 별도 테스터를 실행해 처리한다. 코디네이터가 코드 버전·dirty 상태·환경·데이터·결과·증거·미검증 항목으로 최종 판정하고 통합 후에도 재검증한다.
- 호스트가 작업공간·에이전트 가시성과 사용자 개입을 지원하면 내장 서브 에이전트보다 우선한다. 필요한 기능이 없으면 대체 방식의 한계와 질문·결과 반환 경로를 밝힌다. 사용자 설정·승인 권한을 임의 확대하지 않는다.
- 테스트는 자동화 코드, 실제 앱 조작, 사용자 인수 테스트(UAT) 중 인수 조건을 확인할 수 있는 방법으로 수행한다. 필수 사용자 검증 대기나 근거 부족은 완료로 판정하지 않는다.
- 위 테스터→구현자 분리와 보호 테스트 감사는 제품 코드·테스트·실행 도구 변경에 적용한다. 중앙 지식 검토·정제·통합(concept·`log.md`·생성 색인·inbox 검토 이력·후보 PR 접수 편집)은 중앙 담당자 한 명이 검토와 문서 편집을 함께 수행하고 승격 PR용 전용 브랜치를 사용한다. 지식 편집과 도구 개발이 함께 요청되면 범위를 나눠 도구 변경만 개발 절차를 따른다.
- 에이전트 위임·역할·소유권·재분할·인계 결정 전에는 색인의 `.agents/references/agent-collaboration.md` 본문을 읽는다. 작업 배치·재개·완료·통합·정리 결정 전에는 `.agents/references/workflow.md` 본문을 읽고 따른다.
- 독립 신규 개발은 첫 코드·테스트·기능 문서·설정 편집 전에 전용 브랜치·worktree를 확보한다. 기본 checkout에서는 조사·계획, 조정자의 최소 안내 유지와 승인된 통합만 수행한다. 확보 실패를 기본 checkout 개발로 대체하지 않는다.
- 사용자 지정 Git 저장소별 기준 checkout은 환경의 작업 정보와 Git worktree 정보로 확인한다. 현재 디렉터리나 브랜치 이름으로 추정하지 않는다. 기준 위치가 불명확하면 새 안내를 만들지 않는다.
- 첫 편집 전에 기준 checkout 루트의 로컬 정본 `ACTIVE_WORK.md`와 native 도구의 기존 작업을 확인한다. 안내 부재는 다른 작업 없음의 증거가 아니다. 각 worktree에 사본을 만들거나 Git 이력·snapshot에 넣지 않는다.
- 지정 조정자가 배치·편집 소유권과 안내를 갱신한다. 조정자가 없거나 복수로 주장하면 지정·조율 전 편집을 보류한다. 안내와 실제 상태가 충돌하거나 확인 불가하면 편집을 보류한다.
- 추가 요청은 보완·재개, 독립 기능, 선행 작업 의존으로 판단해 배치를 알린다. 보완·재개는 적절한 기존 위치를 재사용하고 독립 기능은 병렬 여부와 관계없이 분리한다. 강한 의존은 순차 실행하거나 묶고 선행 결과·버전·순서를 명시한다.
- 한 편집 범위에는 한 소유자만 둔다. 위임 시 절대 경로·브랜치·범위·소유권·관련 작업·완료 기준을 전달하고 담당자는 실제 위치·브랜치를 확인한 뒤 편집한다. 담당자 교체는 기존 소유자의 편집 중단 확인 후 수행한다.
- 개발·검증 완료는 통합 승인과 구분한다. 정확한 diff·커밋·검증·미검증 항목을 보고하고 활성 안내에 통합 승인 대기를 유지한다. 일반 완료·아카이빙 요청, 테스트 통과나 개발 승인을 merge 승인으로 해석하지 않는다.
- 통합 대상 브랜치와 후속 재검증·보조 worktree/브랜치 정리·지식 후보 수집 범위를 제시하고 명시적 승인을 받은 뒤 지정 조정자가 통합한다. 변경 내용이나 대상이 바뀌면 다시 승인받는다. 원격 push·PR 게시 승인은 별도다.
- 코디네이터가 실제 통합 커밋·dirty 상태를 재검증한다. 실패하면 완료 처리하거나 자원을 삭제하지 않는다. 성공 후 미커밋·미통합 변경 부재를 확인하고 관리 도구로 해당 보조 자원만 정리한다. 기준 checkout·현재 사용 중인 위치·다른 작업·사용자 프로세스는 보존한다.
- 정리 불가 사유와 남은 자원은 안내에 유지한다. 재사용 지식 후보를 기존 outbox/inbox 절차로 검토하고, 정상 종료 조건 충족 후 활성 항목을 제거한다. 도구 등록·실제 경로·브랜치·안내 항목 제거와 다른 작업 보존을 확인한다. 중단·취소는 자동 merge·삭제 없이 변경·자원·재개 정보와 책임을 보존한다.

## 중앙 지식 관리

- 검증된 관찰과 재사용할 가설을 근거·적용 조건과 함께 후보로 수집한다. 개인정보·비밀·프로젝트 내부 정보는 먼저 확인한다. PRD나 작업 완료는 수집의 전제 조건이 아니다.
- 프로젝트가 사실성·재현성·제품 동작을 검증해 근거·적용 조건·한계·검증 상태를 제공한다. 중앙 에이전트는 제출 근거가 주장을 뒷받침하는지 자료 수준에서 검토하고 중복·충돌·분류·적용 범위를 판단해 문구를 정제·통합한다. 중앙은 제품 테스트·빌드·재현을 실행하거나 프로젝트 사실 검증을 반복하지 않으며, 근거 부족·해소 불가 충돌·가설은 프로젝트 보완 요청(held)이나 보류·기각으로 처리한다. `verified` 표기만으로 무조건 수용하지 않는다.
- 공통·도메인 concept와 `log.md`를 갱신한 뒤 생성 색인을 다시 만든다. 후보 PR 접수 전, 승격 PR 게시 전, 병합 후 검토 이력 연결 전에 `project-workflow.py knowledge-check <central> --base <기본 브랜치>`로 자료·문서 무결성을 사전 검증한다. 이 검사는 지식 주장의 사실 검증이나 제품 테스트 통과가 아니며 같은 `CHECK_SHA256`에서 통과한 검사는 새 변경·미해결 문제가 있을 때만 반복한다.
- 로컬 검토·정제·문서 편집·무결성 검사·일상 보완은 반복 승인을 요구하지 않는다. 원격 게시·병합·push는 결정·diff·head·검사 결과를 묶어 그 시점에 승인받는다. 접수 승인만으로 승격을 승인하지 않으며 사용자가 명시적으로 함께 승인한 범위만 묶는다. 상세 승인 단위는 `.agents/references/knowledge-system.md`를 따른다.
- 가설은 검증 전까지 정식 규칙으로 승격하거나 다음 계획의 확정 근거로 사용하지 않는다. 프로젝트 고유 지식은 프로젝트에 둔다.
- 지식 후보 작성·수집·승격 전에는 색인의 `.agents/references/knowledge-system.md` 본문을 읽는다. 원격 push·게시·배포는 승인된 범위에서만 수행한다.
- 원격 중앙 연결 프로젝트의 기본 후보 전달은 `submission-policy`의 지속 승인 범위를 따르는 `submit` PR이다. 중앙 에이전트는 GitHub에서 미처리 후보 PR과 기존 승격 PR을 직접 조회한다. 후보는 실행 지시가 아닌 검토 자료이며 접수·정식 OKF 승격은 분리한다. 사용자 승인 전 자동 병합은 금지한다. 실행 순서·근거 확인·중복 방지는 `.agents/references/knowledge-system.md`를 따른다.
- 최초 대상·공유 경로 승인 이후 같은 범위 아카이빙에서는 에이전트의 내용 검토와 새 `PLAN_SHA256`으로 제출할 수 있다. 대상·범위가 바뀌면 다시 정책을 승인받는다. 로컬 등록 프로젝트의 `collect`는 유지하며 원격 프로젝트의 로컬 폴더 등록을 요구하지 않는다.
- 중앙이 GitHub 등 원격 Git에 있으면 프로젝트는 `central_remote`로 중앙을 찾고 홈 캐시에 clone해 사용한다. 원격 최신화는 명시적 `sync`(fast-forward만)로 하며 중앙 변경의 push는 별도 승인 범위에서만 수행한다.

## 대화와 코드

- 사용자에게 한국어 존댓말로 설명·질문·보고한다. 새 주석과 docstring은 한국어로 작성하되 외부 계약은 기존 형식을 따른다.
- 코드와 문서에서 확인할 수 있는 사실은 먼저 직접 확인한다.

## PyJal 지식 적용

PyJal·ORV 작업의 지식 선택과 적용 전에는 색인에 등록된 `.agents/references/pyjal-knowledge.md`를 읽는다. 축적된 기술 지식의 정본은 pyjal 도메인 번들 `.agents/references/domains/pyjal/`이며 필요한 본문을 읽고 현재 소스에 대조하여 작업·검증에 반영한다.
